## Critical / High

### 1. Hook subprocess ignores cancellation context — VERIFIED
- **File:** `internal/workflow/workflow.go:324`
- **Severity:** High
- **Category:** Context propagation / cancellation
- **What:** `runHook(context.Background(), hookPath, wtPath)` — the autofix hook is launched with a fresh `context.Background()` instead of the `ctx` passed into `ProcessPR`.
- **Why it matters:** A SIGINT (or batch-level deadline) during a hook run cannot kill the hook. A long-running or hung autofix hook will block the whole PR pipeline regardless of user-driven cancellation.
- **Fix:** `runHook(ctx, hookPath, wtPath)`. Add a regression test that cancels ctx mid-hook and asserts the subprocess exits.

### 2. Stdout silently swapped to nil if both opens fail — VERIFIED
- **File:** `cmd/gh-crfix/main.go:256–268`
- **Severity:** High
- **Category:** Error handling / panic risk
- **What:** Two consecutive open attempts (`runLog.MasterLog()` then `os.DevNull`) both ignore errors via `_,`. The `if devNullOrLog == nil` fallback covers the first failure, but if **both** fail, `os.Stdout = devNullOrLog` sets stdout to a nil `*os.File`. Any subsequent `fmt.Print*` in the dashboard path would panic.
- **Why it matters:** `/dev/null` is essentially always openable, so the failure is unlikely — but the panic mode is silent and global (mutates `os.Stdout`).
- **Fix:** if both opens fail, log a warning and skip the redirection (leave `os.Stdout` untouched), or return an error from the dashboard setup.

### 3. CI check fetch errors are silently dropped — VERIFIED
- **File:** `internal/github/github.go:230–238`
- **Severity:** High
- **Category:** Error handling / observability
- **What:** `FetchFailingChecks` swallows all `gh api` errors with `return nil, nil`. The caller cannot distinguish "API failure" from "no failing checks."
- **Why it matters:** Per existing project memory, surfacing CI failures to the gate/fix models is a deliberate feature. Silent failure here hides a regression where the gate stops seeing CI context — exactly the symptom your `feedback_fix_model_ci_scope.md` memory warns against.
- **Fix:** propagate the error; log at the call site (`workflow.go:373` area). At minimum keep the soft-fail behavior but emit a `Mlog` warning so it shows in the master log.

### 4. Inconsistent `fmt.Sscanf` error handling for CLI flags — VERIFIED
- **File:** `cmd/gh-crfix/main.go:588, 646, 665`
- **Severity:** High (silent misconfiguration)
- **Category:** Error handling / input validation
- **What:** Lines 588, 646, 665 call `fmt.Sscanf(flags[i], "%d", &n)` and discard the return value, while neighboring code (lines 369, 547, 553, 559, 597, 605, 613) checks `if _, err := fmt.Sscanf(...); err == nil { ... }`.
- **Why it matters:** A typo'd `--concurrency abc` silently leaves `n` at zero (or its previous value), then `n` is used to set runtime caps. User sees "running" but with broken concurrency.
- **Fix:** apply the `if _, err := ...; err == nil` pattern uniformly at all three sites. Better: extract a single `parseIntFlag(name, val string, dst *int) error` helper and route all three through it.

## Medium

### 5. `MlogFile` holds the master-log mutex during `io.Copy` — VERIFIED
- **File:** `internal/logs/logs.go:135–149`
- **Severity:** Medium
- **Category:** Concurrency / contention
- **What:** Lock is held across an `io.Copy` of an arbitrarily large file (CI logs can be MBs). All other goroutines blocked on `Mlog`/`MlogFile` stall for the duration.
- **Caveat:** the comment at line 137 explicitly notes this is intentional — to keep the dump contiguous between banner lines. So this is a **deliberate trade-off**, not an unintentional bug. Worth raising only if batch concurrency starts to feel "stuttery."
- **Fix (only if it becomes a problem):** copy under lock into a `bytes.Buffer` cap'd at, say, 8MB chunks; or buffer the entire dump in memory first, then write under lock.

### 6. `ctx` only checked at the start of `ProcessPR` — UNVERIFIED
- **File:** `internal/workflow/workflow.go` around the top of `ProcessPR`
- **Severity:** Medium
- **Category:** Cancellation hygiene
- **What:** Per the agent: `ctx.Err()` is checked once near the entry (~lines 129–132), but not before each subsequent shell-out (worktree create, fetch threads, AI call, reply phase).
- **Why it matters:** SIGINT after the entry check still spawns multi-second `git`/`gh`/`claude` subprocesses. They do receive ctx (so they'll be killed), but cycles are wasted and the run can produce partial state.

## Findings I rejected from the agent's draft

These were in the agent's report but did not survive verification. Listing them so the next reviewer doesn't reopen them.

- **"Temp file cleanup race in `ai.go`."** Wrong. The `defer os.Remove` calls fire when the enclosing Go function returns — that's *after* `runClaudeStructured`/`runCodexStructured` synchronously returns and the subprocess has exited. No race.
- **"Claude flag injection via `--json-schema`."** Wrong. `exec.CommandContext` passes args via `execve`, not a shell. Newlines or quotes in `string(schemaBytes)` cannot break flag parsing or inject extra arguments.
- **"`lockfile_regen.go` won't compile — missing `autoresolve.LockfileKind`."** Wrong. `go build ./...` succeeds.
- **"Data race on `opts.Run` field."** Likely overstated. `ProcessPR` reads `opts` from a closure; `opts.Run` is set once during plan setup and not mutated thereafter. The agent didn't show an actual writer racing with the reader.
